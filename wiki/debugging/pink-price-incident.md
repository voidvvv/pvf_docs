# 案例：粉装售价批量修改的两起事故（负价 + 遗漏）

2026-11-04 批量修改 2,609 件 60 级以上粉装 `[value]` 后游戏实测暴露的两个问题，均已闭环。

## 事故 1：卖价显示 -89,934（int32 溢出）

- **现象**：`fighter/weapon/knuckle/102000371.equ`（85级）设 `[value]`=42,500,000 后，游戏内卖价显示 **-89,934**。
- **根因**：游戏卖价计算有"先乘后除"的 int32 中间量（×100 再 ÷500）：42,500,000×100 = 4,250,000,000 > 2,147,483,647 → 回绕 −44,967,296 → ÷500 截断 = −89,934，**与实测分毫吻合**。
- **修复**：全部降为固定 `[value]`=20,000,000（到手 400 万，低于安全上限 21,474,836）。
- **约束沉淀**：见 [[npc-price]] 的溢出上限节——**写入大数值前先算 int32 边界**。

## 事故 2：2 件遗漏（导出副本 ≠ 封包实况）

- **现象**：`thief/weapon/wand/109030192.equ`（75级）、`mage/weapon/broom/106040334.equ`（85级）未被修改。
- **根因**：批量脚本以**本地导出副本**判断"旧值已等于目标 → 跳过导入"；但封包实况是原版值（101,120 / 128,160）。导出副本在这两个文件上与封包不一致（疑似用户此前手工实验改过本地副本）——**错误的数据源信任**。
- **修复**：以封包实况为准补导入；全量审计（3,628 件逐件 GetFileContent 比对，26 秒）确认无其他遗漏。
- **教训**：
  1. **数据源信任层级：封包实况（API 实时读）> 本地导出副本**。任何"无需修改/已达标"的跳过判断，必须对封包实况验证，不能信副本；
  2. 大批量写操作后必须**脚本化全量回读审计**（本例 26s/3,628 件，成本极低）；
  3. 回滚清单要记录**封包原值**而非副本旧值。

## 后续：第二轮实测推翻乘数模型（方法论补课）

v2 修复采用"×100 模型"推的 20,000,000（到手应为 400 万），游戏实测却显示 **−294,967**：

- 数值反推：4,000,000 − (−294,967) = 4,294,967 = 2^32÷1000，说明除数是 1000（乘数 ×200）而非 500；
- **×100 模型被第二个数据点淘汰**；×200 与 ×1000 均同时吻合两个数据点；
- 终版方案（用户确认）：固定 `[value]`=2,000,000（到手 40 万）——在所有存活模型下均安全。

**教训（模型选择方法论）**：
1. 一个数据点常有多条公式同解（本例 ×100/×200/×1000 全拟合 −89,934），**不能凭"看起来合理"的旁证选分支**——本例的旁证（原版 7.5M 物品卖价正常）本身未经验证、且出自被污染的导出副本；
2. 多模型并存时：要么用**判别性探针**（如 2,500,000 在 ×200/×1000 下显示不同），要么直接取**全模型安全值**（min 上限）；
3. int32 回绕推演用 Python 复现时注意阈值是 2^31（有符号），不是 2^32。

## 排查工具链（可复用）

- 直连 `GET /Api/PvfUtiltiy/GetFileContent` 单件读回（见 [[pvfutility-mcp]] 直连节）；
- 分层抽样验证（等级/部位覆盖）→ 异常时升级为全量审计；
- 溢出推演：用 Python 复现 int32 回绕（注意 **int32 阈值是 2^31 不是 2^32**——本次排查脚本曾在此踩坑）。
